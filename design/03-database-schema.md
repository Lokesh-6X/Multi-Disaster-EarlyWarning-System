# 3. Database Schema

PostgreSQL 16/17 with TimescaleDB 2.x, one database per installation (one site, D26). This document defines every table, its keys and indexes, the TimescaleDB hypertables, continuous aggregates, compression and retention, and the normalization rules that keep the schema both consistent and fast.

Decisions referenced: DD21–DD28 in [decisions.md](decisions.md). Owners of each table (the only process that writes it) follow [01 §1.2](01-architecture.md).

## 3.1 Conventions

| Topic | Rule |
|---|---|
| Names | `snake_case`, singular table names (`alert`, `kit`) |
| Time | `timestamptz`, always UTC (NFR-06) |
| Measurements | `real` (4 bytes, 6–7 significant digits; enough for every sensor in [02 §2.1](../requirements/02-hardware.md)); coordinates `double precision` |
| Kit key | `kit.kit_no smallint` is the internal key used in every other table; `kit.kit_id text` (e.g. `KIT-01`) is the external key from the MQTT contract and the API (DD22) |
| Other keys (DD22) | High-volume or high-fan-out rows: `bigint` identity (`forecast_run`, `alert_change`, `external_forecast`). Entities addressed by the API: `uuid` generated by the application as **UUIDv7** (time-ordered, so B-tree inserts stay at the right edge). The API exposes all IDs as opaque strings ([02 §2.1](02-api.md)) |
| Fixed vocabularies | PostgreSQL `ENUM` types (4 bytes, ordered by declaration, so `level >= 'orange'` works). A lookup table only where the value has attributes (`hazard_event`) (DD26) |
| Booleans and sets | No arrays or JSON lists of facts; a set is a child table (1NF) |
| JSONB | Only for a single typed value (`config_value.value`, `audit_change.old_value/new_value`) and for read-only metadata mirrored from `config/defaults.yaml` (`config_key.rules`) |
| Migrations | Alembic; TimescaleDB calls (`create_hypertable`, policies) are plain SQL inside migrations. Tables are grouped by topic below, not in creation order; migrations create them in dependency order and add circular foreign keys (`alert` ↔ `alert_change` ↔ `alert_command`) with `ALTER TABLE` |
| Extensions | `timescaledb`, `citext` (case-insensitive e-mail addresses) |

## 3.2 Normalization policy (DD21)

**Relational data is in BCNF**: every non-key column depends on the key, the whole key and nothing but the key.

| Rule | Applied as |
|---|---|
| 1NF: no repeating groups or lists | Recipient hazards and zones, user e-mail preferences, audit field changes, QC flags and models used by a run are all child tables |
| 2NF/3NF: no partial or transitive dependencies | `hazard` is not stored on alerts; it follows from `event` through `hazard_event`. A forecast row does not repeat the run's `issue_time`; hypertables are partitioned by the integer `run_id` instead (DD25). Kit zone, position and exposure live only in kit configuration, not on the `kit` row |
| One fact, one place | Current kit status = latest `kit_status_event`; outages = pairs of events (view); lead time = event start − first alert (computed); effective config = resolved on read |
| Time-series rows | One wide row per `(kit_no, ts)` with one column per measurement. Every column depends on the full key, so the row is in 3NF; this is faster than one row per variable (5–10× fewer rows and index entries) |

**Deliberate, documented denormalizations** (each is either required by a requirement or removes a hot-path join or a recomputation):

| # | Stored although derivable | Why |
|---|---|---|
| N1 | `reading_clean` and `reading_derived` (derivable from `reading_raw` + the kit and site config versions) | Required by DP-03; every consumer reads them. `kit_config_version_id` and `site_config_version_id` are kept so any row can be recomputed and audited (DD123) |
| N2 | Continuous aggregates `reading_15m`, `reading_1h` | Required by DP-07; maintained incrementally by TimescaleDB, including late data (DP-08) |
| N3 | `alert.closed_at` (also the time of the closing `alert_change`) | Enables the partial unique index "one open alert per key" and a tiny partial index for active alerts |
| N4 | `threshold_value` on `forecast_probability` and `alert_change` | System defaults are shipped in `defaults.yaml` and change with software versions; storing the applied value keeps history correct (AL-16) |
| N5 | `email_message.to_address`, `email_message.subject` | The address and subject actually used at send time; the recipient's address may change later |
| N6 | `verification_daily` (sums of errors per day) | Live accuracy report (`/reports/accuracy?source=live`) without scanning a year of forecasts |

## 3.5 Site, kits and configuration

### 3.5.1 Site and kits

```sql
CREATE TABLE site (
  id          smallint PRIMARY KEY DEFAULT 1 CHECK (id = 1),          -- exactly one row (D26)
  site_id     text NOT NULL UNIQUE CHECK (site_id ~ '^[a-z0-9-]{2,32}$'),  -- MQTT topic segment
  created_at  timestamptz NOT NULL,
  locked_at   timestamptz            -- set when the first kit connects; site_id immutable afterwards
);

CREATE TABLE kit (
  kit_no      smallint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kit_id      text NOT NULL UNIQUE CHECK (kit_id ~ '^[A-Za-z0-9_-]{1,32}$'),  -- CFG-03 unique kit_id
  created_at  timestamptz NOT NULL
);

CREATE TABLE kit_firmware (            -- firmware history; replaces a repeated fw column per reading
  kit_no        smallint NOT NULL REFERENCES kit,
  first_seen_at timestamptz NOT NULL,
  fw            text NOT NULL,
  PRIMARY KEY (kit_no, first_seen_at)
);
```

Everything else about the site (name, coordinates, elevation, timezone, region type) and about a kit (zone, coordinates, elevation, mount height, exposure, calibration, enabled sensors, `enabled`) is **configuration** and lives in §3.5.2, so it is versioned once, in one place. A kit is retired with `enabled = false`, never deleted.

The firmware of any reading is the `kit_firmware` row with the latest `first_seen_at <= ts`; `ingest` adds a row only when the reported `fw` changes. The raw `fw` value is therefore kept losslessly (DP-03) without repeating it on every row.

### 3.5.2 Versioned configuration (DD23)

```sql
CREATE TABLE config_key (              -- mirror of config/defaults.yaml, synced by start.ps1 (DD110), read-only
  key           text PRIMARY KEY,
  deprecated    boolean NOT NULL DEFAULT false,   -- removed from defaults.yaml; never deleted (old versions reference it)
  value_type    text NOT NULL CHECK (value_type IN ('number', 'integer', 'string', 'boolean', 'integer_list')),
  default_value jsonb,                 -- NULL = no static default (e.g. site latitude, region-dependent keys)
  computed_from text,                  -- e.g. 'onboarding.rain_1h_wet_percentile' (04 §4.2)
  site_allowed  boolean NOT NULL,      -- CFG-02 override scope
  kit_allowed   boolean NOT NULL,
  required_at   config_scope,          -- level where a value must exist (e.g. lat at site)
  unit          text,
  rules         jsonb NOT NULL DEFAULT '{}',   -- min, max, allowed values, ordering groups (04)
  description   text NOT NULL
);

CREATE TABLE config_key_region_default (   -- defaults that depend on region type (heatwave rules)
  key         text NOT NULL REFERENCES config_key ON DELETE CASCADE,
  region_type text NOT NULL CHECK (region_type IN ('plains', 'coastal', 'hilly')),
  value       jsonb NOT NULL,
  PRIMARY KEY (key, region_type)
);

CREATE TABLE config_version (
  id          integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  scope       config_scope NOT NULL,
  kit_no      smallint REFERENCES kit,
  version     integer NOT NULL CHECK (version >= 1),
  created_at  timestamptz NOT NULL,
  created_by  uuid REFERENCES app_user,
  reason      text,
  CHECK ((scope = 'kit') = (kit_no IS NOT NULL)),
  UNIQUE NULLS NOT DISTINCT (scope, kit_no, version)       -- optimistic locking, see below
);

CREATE TABLE config_value (            -- the full set of values defined at that level in that version
  version_id  integer NOT NULL REFERENCES config_version ON DELETE CASCADE,
  key         text NOT NULL REFERENCES config_key,
  value       jsonb NOT NULL CHECK (jsonb_typeof(value) IN ('number', 'string', 'boolean', 'array')),  -- array only for integer_list keys
  PRIMARY KEY (version_id, key)
);
```

- **Optimistic locking for free (CFG-04, WEB-22):** a save based on version *n* inserts version *n + 1*. If anyone else already saved *n + 1*, the unique constraint fails and the API returns `409 CONFIG_VERSION_CONFLICT`. No locks, no read-then-write race.
- **Current version** of a scope = highest `version`; the unique index answers it with one index lookup.
- **Override scope (CFG-02)** is checked against `config_key.site_allowed` / `kit_allowed` on save; type is checked against `value_type`.
- **History (CFG-05, AL-16)**: versions are never updated or deleted; `/config/history` is a query, and diffs are computed between consecutive versions.
- **Effective values (CFG-06)** are resolved, never stored. The authoritative resolver is `ews.common.config` ([04 §4.2](04-configuration.md)), which also applies region and onboarding-computed defaults; the view below covers kit → site → static default and is used for SQL checks and debugging:

```sql
CREATE VIEW config_current AS
  SELECT DISTINCT ON (scope, kit_no) id, scope, kit_no, version
  FROM config_version ORDER BY scope, kit_no, version DESC;

CREATE VIEW config_effective_kit AS            -- one row per kit and key, with its source
  SELECT k.kit_no, ck.key,
         COALESCE(kv.value, sv.value, ck.default_value) AS value,
         CASE WHEN kv.value IS NOT NULL THEN 'kit'
              WHEN sv.value IS NOT NULL THEN 'site' ELSE 'default' END AS source
  FROM kit k
  CROSS JOIN config_key ck
  LEFT JOIN config_current kc ON kc.scope = 'kit' AND kc.kit_no = k.kit_no
  LEFT JOIN config_value  kv ON kv.version_id = kc.id AND kv.key = ck.key
  LEFT JOIN config_current sc ON sc.scope = 'site'
  LEFT JOIN config_value  sv ON sv.version_id = sc.id AND sv.key = ck.key;
```

Processes cache the resolved result in memory and reload on `config.changed` ([01 §1.3.3](01-architecture.md)).

### 3.5.3 Alert recipient lists

Recipient lists are site configuration (D24, WEB-41), but they are sets of records, so they get their own tables instead of a JSON list. Each row carries its own `version` for optimistic locking (CFG-04); changes are audited and announced with `config.changed`.

```sql
CREATE TABLE recipient (
  id         uuid PRIMARY KEY,
  email      citext NOT NULL UNIQUE,
  label      text NOT NULL,                 -- e.g. "Site mailing list", "Sports department"
  min_level  alert_level NOT NULL DEFAULT 'yellow',
  active     boolean NOT NULL DEFAULT true,
  version    integer NOT NULL DEFAULT 1,
  created_at timestamptz NOT NULL,
  updated_at timestamptz NOT NULL
);

CREATE TABLE recipient_hazard (            -- which hazards this recipient receives
  recipient_id uuid NOT NULL REFERENCES recipient ON DELETE CASCADE,
  hazard       hazard NOT NULL,
  PRIMARY KEY (recipient_id, hazard)
);

CREATE TABLE recipient_zone (              -- local-risk routing (04 §4.6); no rows = all zones
  recipient_id uuid NOT NULL REFERENCES recipient ON DELETE CASCADE,
  kit_no       smallint NOT NULL REFERENCES kit,
  PRIMARY KEY (recipient_id, kit_no)
);
```

## 3.6 Readings (hypertables)

### 3.6.1 Raw, clean and derived (DD24)

```sql
CREATE TABLE reading_raw (                 -- exactly what the kit sent (DP-03); owner: ingest
  kit_no           smallint NOT NULL REFERENCES kit,
  ts               timestamptz NOT NULL,   -- kit timestamp (UTC, HW-06)
  received_at      timestamptz NOT NULL,   -- server receive time (DP-01)
  seq              bigint NOT NULL,
  bme_temp_c       real NOT NULL,
  bme_rh_pct       real NOT NULL,
  bme_pressure_hpa real NOT NULL,
  dht_temp_c       real,
  dht_rh_pct       real,
  wind_avg_kmh     real NOT NULL,
  wind_gust_kmh    real NOT NULL,
  wind_dir_deg     real,
  rain_tips        smallint NOT NULL,
  rssi_dbm         smallint,
  uptime_s         integer,
  PRIMARY KEY (kit_no, ts)                 -- DP-02: duplicates rejected by INSERT … ON CONFLICT DO NOTHING
);

CREATE TABLE reading_clean (               -- calibrated, converted, QC applied; owner: ingest
  kit_no            smallint NOT NULL REFERENCES kit,
  ts                timestamptz NOT NULL,
  kit_config_version_id  integer NOT NULL REFERENCES config_version,  -- kit config used (recompute, audit)
  site_config_version_id integer NOT NULL REFERENCES config_version,  -- site config used (elevation fallback, QC limits; DD123)
  temp_c            real,                  -- NULL when faulty (excluded, §3.3 of requirements 03)
  temp_sensor       temp_sensor,           -- bme280 normally, dht11 when BME280 is faulty
  rh_pct            real,
  pressure_msl_hpa  real,                  -- DP-05
  wind_avg_kmh      real,
  wind_gust_kmh     real,
  wind_dir_deg      real,
  rain_mm           real,                  -- DP-04
  PRIMARY KEY (kit_no, ts)
);

CREATE TABLE reading_derived (             -- DP-06 features at each reading; owner: ingest
  kit_no                   smallint NOT NULL REFERENCES kit,
  ts                       timestamptz NOT NULL,
  heat_index_c             real,
  rain_rate_mmh            real,
  rain_1h_mm               real,
  rain_3h_mm               real,
  rain_24h_mm              real,
  pressure_tendency_1h_hpa real,
  pressure_tendency_3h_hpa real,
  gust_trend_15m_kmh       real,
  gust_trend_30m_kmh       real,
  gust_trend_60m_kmh       real,
  temp_change_30m_c        real,
  PRIMARY KEY (kit_no, ts)
);

CREATE TABLE reading_qc_flag (             -- one row per failed check (1NF); owner: ingest
  kit_no      smallint NOT NULL REFERENCES kit,
  ts          timestamptz NOT NULL,
  measurement measurement NOT NULL,
  check_kind  qc_check NOT NULL,
  severity    qc_severity NOT NULL,
  observed    real,
  detail      text,
  PRIMARY KEY (kit_no, ts, measurement, check_kind)
);
```

- A measurement is **valid** when it has no flag, **suspicious** when its worst flag is `suspicious`, **faulty** when it is `faulty`; faulty values are `NULL` in `reading_clean` (the raw value stays in `reading_raw`). The reading's overall QC status in the API is the worst flag of that `(kit_no, ts)`; it is not stored.
- QC is per measurement: a stuck humidity sensor does not discard the wind and rain of the same minute.
- Clock offset and lateness (DP-01, DP-08) are derived from `received_at − ts` in `reading_raw`; they are neither stored nor flagged ([05 §5.4.7](05-data-pipeline.md)).
- Station pressure after calibration (`bme_pressure_hpa + offset`) is not stored; it follows from raw + config version.
- Feature definitions and algorithms: [05](05-data-pipeline.md).

### 3.6.2 Resampled series (continuous aggregates)

```sql
CREATE MATERIALIZED VIEW reading_15m WITH (timescaledb.continuous, timescaledb.materialized_only = false) AS
SELECT kit_no,
       time_bucket('15 minutes', ts) AS bucket,
       avg(temp_c)            AS temp_c,
       max(temp_c)            AS temp_max_c,
       avg(rh_pct)            AS rh_pct,
       avg(pressure_msl_hpa)  AS pressure_msl_hpa,
       avg(wind_avg_kmh)      AS wind_avg_kmh,
       max(wind_gust_kmh)     AS wind_gust_kmh,
       sum(rain_mm)           AS rain_mm,
       count(*)               AS n_readings,     -- completeness (offline gaps, HW-09)
       count(temp_c)          AS n_temp_valid
FROM reading_clean
GROUP BY kit_no, bucket;

SELECT add_continuous_aggregate_policy('reading_15m',
  start_offset      => INTERVAL '3 hours',    -- late messages up to 3 h are folded in (DP-08)
  end_offset        => INTERVAL '2 minutes',  -- grace period (DP-08)
  schedule_interval => INTERVAL '1 minute');
```

`reading_1h` is defined the same way with `time_bucket('1 hour', ts)` and `start_offset => INTERVAL '26 hours'`. Both read `reading_clean` directly (not hierarchical), so averages are true averages. `materialized_only = false` makes the newest, not-yet-materialized bucket visible in queries. The final column list (incl. `temp_min_c`, circular wind direction and per-measurement counts) and the consumer views `series_15m` / `series_1h` (end-labelled time, coverage rule) are in [05 §5.7](05-data-pipeline.md).

```sql
CREATE TABLE qc_neighbour_spread (         -- learned spread for the neighbour check (DP-24); owner: worker (nightly)
  kit_no      smallint NOT NULL REFERENCES kit,
  measurement measurement NOT NULL,
  spread      real NOT NULL,
  computed_at timestamptz NOT NULL,
  PRIMARY KEY (kit_no, measurement)
);
```

### 3.6.3 Kit status and rejected messages

```sql
CREATE TABLE kit_status_event (            -- DP-13; owner: ingest
  kit_no  smallint NOT NULL REFERENCES kit,
  at      timestamptz NOT NULL,
  status  kit_status NOT NULL,
  source  status_source NOT NULL,
  PRIMARY KEY (kit_no, at)
);

CREATE VIEW kit_outage AS                  -- offline → next online, for the kit-health page
  SELECT kit_no, at AS offline_at, next_at AS online_at, source
  FROM (SELECT kit_no, at, status, source,
               lead(at) OVER (PARTITION BY kit_no ORDER BY at) AS next_at
        FROM kit_status_event) e
  WHERE status = 'offline';

CREATE TABLE rejected_message (            -- DP-12; owner: ingest
  id              bigint GENERATED ALWAYS AS IDENTITY,
  received_at     timestamptz NOT NULL,
  topic           text NOT NULL,           -- contains the claimed site_id and kit_id
  kit_no          smallint REFERENCES kit, -- NULL when the kit is unknown
  reason_code     reject_reason NOT NULL,
  detail          text NOT NULL,           -- readable explanation, e.g. "bme_rh_pct: expected number"
  payload_excerpt text NOT NULL,           -- first 2 KB
  PRIMARY KEY (id)
);
```

Current kit status is the latest `kit_status_event` per kit (`ORDER BY at DESC LIMIT 1` on the primary key). Last reading time is the latest `reading_clean.ts` for the kit (same index pattern).

### 3.9.2 Alert and its changes (DD27)

An **alert** is an identity (what, where, which source) with a pointer to its **current change**. Every change is an append-only row holding the full state after that change. Reading the current state is one primary-key join; history is a range scan; nothing is updated in place except the pointer and `closed_at`.

```sql
CREATE TABLE alert (                       -- owner: alerts
  id                uuid PRIMARY KEY,
  event             text NOT NULL REFERENCES hazard_event,
  source            alert_source NOT NULL,
  scope             scope_kind NOT NULL,
  kit_no            smallint REFERENCES kit,
  opened_at         timestamptz NOT NULL,
  closed_at         timestamptz,           -- N3
  current_change_id bigint NOT NULL,       -- FK added below (deferred)
  advice_override   text,                  -- operator advice; NULL = configured advice (owner: api)
  CHECK ((scope = 'kit') = (kit_no IS NOT NULL))
);
CREATE UNIQUE INDEX alert_one_open
  ON alert (event, source, COALESCE(kit_no, 0)) WHERE closed_at IS NULL;

CREATE TABLE alert_change (                -- AL-08 history; owner: alerts
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  alert_id        uuid NOT NULL REFERENCES alert,
  seq             smallint NOT NULL,
  at              timestamptz NOT NULL,
  change          alert_change_kind NOT NULL,
  trigger         alert_trigger NOT NULL,
  related_alert_id uuid REFERENCES alert,  -- taken_over: the Live alert that replaced this one
  status          alert_status NOT NULL,
  type            alert_type NOT NULL,
  level           alert_level NOT NULL,
  probability     real,                    -- NULL for live and manual
  threshold_value real,                    -- N4
  window_start    timestamptz,
  window_end      timestamptz,
  run_id          bigint REFERENCES forecast_run,
  command_id      uuid REFERENCES alert_command,
  explanation     text,                    -- e.g. "3 consecutive runs below 45 %"
  UNIQUE (alert_id, seq)
);
ALTER TABLE alert ADD FOREIGN KEY (current_change_id) REFERENCES alert_change
  DEFERRABLE INITIALLY DEFERRED;           -- alert and first change inserted in one transaction

CREATE TABLE alert_run_probability (       -- AL-13 probability trend, one row per run per open forecast alert
  alert_id    uuid NOT NULL REFERENCES alert,
  run_id      bigint NOT NULL REFERENCES forecast_run,
  probability real NOT NULL,
  PRIMARY KEY (alert_id, run_id)
);
```

The `alert_one_open` index guarantees the engine never opens a duplicate alert for the same event, source and zone. Forecast and live alerts for the same hazard are separate alerts (Scenario 2), because `source` is part of the key.

```sql
CREATE TABLE alert_command (               -- DD2, 02 §2.5; api inserts, alerts updates status
  id             uuid PRIMARY KEY,

  id         uuid PRIMARY KEY,
  alert_id   uuid NOT NULL REFERENCES alert,
  command_id uuid NOT NULL REFERENCES alert_command,   -- who, why, until: on the command
  ended_at   timestamptz,
  ended_how  suppression_end
);
CREATE UNIQUE INDEX alert_one_suppression ON alert_suppression (alert_id) WHERE ended_at IS NULL;
```

- **Every escalation needs its own acknowledgement (DD36).** An escalation is a `created` or `upgraded` change; `upgraded` means a higher level (yellow → orange → red) or a more serious type (watch → warning → live; enum order). Downgrades and other changes keep the existing acknowledgement.
- **Acknowledgement is atomic by construction**: the API inserts `(alert_id, change_id = latest escalation of that alert)` with `ON CONFLICT DO NOTHING RETURNING …`, in one statement. If nothing is returned, the API reads the existing row and answers `409 ALREADY_ACKNOWLEDGED` with its user and time. An alert "needs acknowledgement" when its latest escalation has no row; the old rows remain as acknowledgement history.
- The suppression's reason, author and expiry are not copied; they are on its `alert_command`.

## 3.13 Indexes and query patterns

Primary keys and the unique/partial indexes above cover most queries. Additional indexes:

| Index | Serves |
|---|---|
| `reading_raw (kit_no, received_at)` | Alert live path catch-up (§3.12) |
| `reading_qc_flag (ts)` *(hypertable time index)* | QC list per kit uses the PK `(kit_no, ts, …)` |
| `rejected_message (kit_no, received_at DESC)`, `(received_at DESC)` | `/rejected-messages` |
| `forecast_value (kit_no, variable, target_time)` | Live verification by target time |
| `forecast_probability (kit_no, event, window_start)` | Probability views across runs |
| `alert (opened_at DESC)` | `/alerts?status=all` (cursor) |
| `alert (opened_at) WHERE closed_at IS NULL` | `/alerts` (active), `/live`, banner |
| `alert_change (alert_id, seq)` *(unique)* | Alert history |
| `alert_note (alert_id, at)` | Alert detail |
| `email_message (alert_change_id)` | Emails per alert, cooldown lookup |
| `audit_entry (at DESC)`, `(actor_id, at DESC)`, `(entity_type, entity_id, at DESC)` | `/audit` filters (cursor) |
| `config_version (created_by)` | FK lookups |

Hot paths and how they are answered:

| API call ([02](02-api.md)) | Query shape | Cost |
|---|---|---|
| `GET /live` | Latest row per kit from `reading_clean` + `reading_derived` (PK, `ORDER BY ts DESC LIMIT 1` per kit), flags for that row, latest status event, open alerts (partial index) | A few index lookups per kit |
| `GET /kits/{id}/readings?resolution=15m` | Range scan on `reading_15m` | One chunk per week |
| `GET /forecast/latest` | Latest completed `forecast_run`, then `forecast_value WHERE run_id = …` | One chunk; cached per run in `api` |
| `GET /alerts` (active) | Partial index on open alerts + PK join to `alert_change` | Tens of rows |
| `POST /alerts/{id}/acknowledge` | One `INSERT … ON CONFLICT DO NOTHING` | Atomic, no lock wait |
| `PUT /config/kits/{id}` | Insert version + values in one transaction; unique key detects conflicts | No locks |
| mailer poll | Partial index `email_queue` | Only queued rows |

| `reading_qc_flag` | `ts`, 30 days | `kit_no` / `ts DESC`, 30 days | 1 year |
| `reading_15m`, `reading_1h` | continuous aggregates | 30 days | Keep all |
| `forecast_value` | `run_id`, 672 runs | `kit_no, variable` / `target_time`, 2 days | 400 days |
| `forecast_probability` | `run_id`, 672 runs | `kit_no, event` / `window_start`, 2 days | 400 days |
| `external_forecast_value` | `external_forecast_id`, 168 fetches | `variable` / `target_time`, 7 days | 400 days |
| `history_hourly` | `ts`, 1 year | `dataset_id` / `ts`, at insert | Latest two datasets |
| Regular tables: `rejected_message` | — | — | 30 days (worker cleanup job) |
| `user_session`, `user_token` | — | — | Deleted 1 day / 30 days after expiry |
| `alert*`, `email_*`, `audit_*`, `config_*`, `kit_status_event` | — | — | Keep all |

Integer hypertables need an "integer now" function for policies (`set_integer_now_func`, returning the latest `forecast_run.id`). Retention values become config keys in [04](04-configuration.md).

- **Run IDs are not days.** "672 runs ≈ 7 days" assumes 96 IDs per day; shadow runs (24 per day when enabled) and failed runs also take IDs. The forecast retention job therefore does not use a fixed ID distance: it looks up the newest run with `issue_time` older than `retention_forecast_days` and drops chunks below its ID (analysis AN-24).
- **Demo database (DD107):** in a database marked `ews.is_demo = on` the migrations create **no retention and no compression policies**. TimescaleDB jobs use the real clock, so historical demo dates (e.g. 2024) would be dropped or compressed during a demo. Continuous-aggregate refresh policies stay (old buckets are served by the real-time part of the aggregate).

### Size estimate (per kit per year)

| Data | Rows | Uncompressed | Compressed (≈ 10×) |
|---|---|---|---|
| Raw + clean + derived readings | 3 × 525 600 | ≈ 120 MB | ≈ 12 MB |
| Forecast values (96 runs/day × 5 variables × 72 h) | 12.6 M | ≈ 650 MB | ≈ 65 MB |
| Forecast probabilities (≈ 70 per run) | 2.5 M | ≈ 200 MB | ≈ 20 MB |
| Site history (once, 30 years hourly) | 263 000 | ≈ 20 MB | ≈ 3 MB |

Five kits stay well under 1 GB per year: comfortable on a laptop.
