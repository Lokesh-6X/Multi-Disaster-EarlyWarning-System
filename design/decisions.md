# Design Decisions

Important design choices with their reasons. Requirement-level decisions (D1–D39) are in [requirements/09](../requirements/09-decisions-and-open-questions.md); this file records choices made during design. Numbering is permanent: a revised decision keeps its number and is marked **Revised**.

| # | Decision | Reason | Document |
|---|---|---|---|
| DD1 | The backend runs as **five processes** built from one Python package `ews`: `api`, `ingest`, `worker`, `alerts`, `mailer` | CPU-heavy inference must not delay squall Live alerts (AL-02) or WebSocket pushes (NFR-01); slow SMTP retries must not block alerting. Shared code keeps merging cheap | [01 §1.1](01-architecture.md) |
| DD2 | `alerts` is the **only writer of alert state**. Acknowledgements and notes are written directly by `api`; suppress / manual alert commands go through an operator command table applied by `alerts` | No races between live path, forecast path and operators; suppression safety override (AL-15) and notifications follow one state machine | [01 §1.2](01-architecture.md) |
| DD3 | **PostgreSQL is the hand-off between processes**: data in tables, `LISTEN/NOTIFY` only as a wake-up, consumers catch up from stored markers. No Redis, no internal MQTT topics | Nothing extra to install; events are visible only after commit; a missed notification loses nothing | [01 §1.3.2](01-architecture.md) |
| DD4 | **APScheduler** inside `worker`; no Celery (**Revised:** a clock loop on `ews.common.clock` instead of APScheduler, D41, DD130) | Celery needs an extra message broker; local-only install (NFR-05). Requirements 08 §8.4 updated | [01 §1.2](01-architecture.md) |
| DD5 | **Transactional email outbox**: alert changes and their outbox rows are written in one transaction; `mailer` is the only sender, behind a channel interface | Reliable sending with retries, dedup and send log (WEB-26, WEB-44); a new channel (F1, F2) can be added without touching the alert engine (07 §7.6) | [01 §1.2](01-architecture.md) |
| DD6 | `ingest` **owns kit status**: status topic and the no-data timeout | One owner for online/offline and outage history (DP-09, DP-13) | [01 §1.2](01-architecture.md) |
| DD7 | The **simulator is a separate program** that does not import backend code and speaks only the MQTT contract, using the same broker users and ACL as real kits | It behaves exactly like an external kit, so end-to-end tests (TST-14) are honest | [01 §1.6](01-architecture.md) |
| DD8 | **One site per installation** (requirements D26). The `{site_id}` in topics must match the installation's site; `site_id` is fixed once kits have connected | Owner decision; simpler UI, permissions and data model; a new site is a new installation with configuration only (NFR-07) | [01 §1.1](01-architecture.md) |
| DD9 | Frontend: **React + Vite + TypeScript**, API types generated from FastAPI's OpenAPI schema. The built app is served by `api` on port 8000; the Vite dev server is used only in development | One port for the demo; frontend types always match the API | [01 §1.7](01-architecture.md) |
| DD10 | **Training is offline** in `ml/` (**Revised:** Kaggle instead of Colab, D40, DD128); the backend only loads versioned model files from `models/` with a committed `registry.json`. Shared feature code lives in `backend/ews/ml/` | Training needs GPU and heavy dependencies; identical features in training and inference; model versions recorded per forecast (ML-09) | [01 §1.6](01-architecture.md) |
| DD11 | **Mosquitto security**: no anonymous access, password file, ACL limiting each kit to its own topics; `ingest` uses QoS 1 with a persistent session and broker persistence on; **Revised:** queue limit removed (DD109) | NFR-08; readings published while `ingest` restarts are not lost; duplicates removed by DP-02 | [01 §1.3.1](01-architecture.md) |
| DD12 | **PowerShell start/stop scripts** with a restart wrapper and one log file per process; every process writes a **heartbeat** row (design addition) | NFR-05; crashed processes come back; failures are visible to admins and during the demo | [01 §1.5, §1.7](01-architecture.md) |
| DD13 | **No process keeps important state only in memory**: timers, cooldowns and suppressions are stored as timestamps; processed-up-to markers are stored in the database | A restart resumes exactly where it stopped | [01 §1.3.2](01-architecture.md) |
| DD14 | **Cookie sessions**: random session ID in an `HttpOnly`, `SameSite=Strict` cookie, stored hashed server-side, 8 h absolute expiry, CSRF token header on writes; the WebSocket uses the same cookie plus an `Origin` check | Deactivation and logout end sessions immediately (WEB-04, WEB-06); no tokens readable by page scripts; one mechanism for REST and WebSocket | [02 §2.2](02-api.md) |
| DD15 | **Errors are RFC 9457 problem details plus a stable `code`** and `errors[]` for field validation | A standard format; the frontend switches on `code`, not on message text | [02 §2.3](02-api.md) |
| DD16 | **Operator commands wait up to 3 s, then return 202**: `200` with the updated alert when the alert engine applies the command in time, `202` with a command ID otherwise; result also pushed over WebSocket | Normal case feels synchronous; still correct when `alerts` is slow or restarting (DD2) | [02 §2.5](02-api.md) |
| DD17 | **One WebSocket stream per client**, all events the role may see, no subscriptions and no replay; after every (re)connect the client reloads state over REST | Simplest protocol that still meets NFR-01 and NFR-04; no gap handling needed | [02 §2.7](02-api.md) |
| DD18 | **Base path `/api/v1`** | A breaking change can live beside the old version | [02 §2.1](02-api.md) |
| DD19 | **Cursor pagination** (time + ID) for lists; time-series endpoints are range-bounded with per-resolution limits | Stable pages while new rows arrive every minute; efficient on hypertables | [02 §2.1](02-api.md) |
| DD20 | **`reason` is required** on writes that change configuration, users or alerts (suppress, manual alert, clear), optional elsewhere | Gives the "why" of the audit log (WEB-25) where it matters, without slowing acknowledgements | [02 §2.1](02-api.md) |
| DD21 | **Normalization policy**: relational data in BCNF (sets as child tables, no JSON lists, no transitive columns); time series as wide rows keyed by `(kit_no, ts)` (3NF); six deliberate denormalizations N1–N6, each listed with its reason | Consistency without paying for joins or recomputation on hot paths; wide rows are 5–10× fewer rows than one row per variable | [03 §3.2](03-database-schema.md) |
| DD22 | **Keys**: `smallint kit_no` internally, `kit_id` text externally; `bigint` identity for high-volume rows (runs, alert changes); application-generated **UUIDv7** for API-addressed entities | Small keys on hypertables; time-ordered UUIDs keep B-tree inserts cheap; IDs stay opaque to clients | [03 §3.1](03-database-schema.md) |
| DD23 | **Configuration as versioned key/value rows**: `config_version` + `config_value`, unique `(scope, kit_no, version)`; site and kit attributes are config keys, not table columns; effective values from a view | One versioning mechanism for everything (CFG-04, CFG-05); the unique key implements optimistic locking with no locks; full history for free | [03 §3.5.2](03-database-schema.md) |
| DD24 | **Three reading hypertables** (raw, clean, derived) + per-measurement QC flag rows; 15-minute and hourly series as **TimescaleDB continuous aggregates** with a 2-minute end offset and a 3-hour refresh window | DP-03 separation; QC per measurement keeps good values of the same minute; late data handled by the database (DP-08), no resampling code in `worker` | [03 §3.6](03-database-schema.md) |
| DD25 | **Forecast tables are integer hypertables partitioned by `run_id`** (672 runs per chunk); the models used are recorded per run and output in `forecast_run_model` | A run is read from one chunk; `issue_time` is not repeated on millions of rows; retention drops whole weeks | [03 §3.7.2](03-database-schema.md) |
| DD26 | **PostgreSQL enums** for fixed vocabularies (ordered, so `level >= 'orange'` works); lookup table only for `hazard_event`, which carries hazard and variable | Small, fast, self-validating columns; `hazard` derived from `event`, not stored | [03 §3.4](03-database-schema.md) |
| DD27 | **Alert = identity + pointer to its current change**; changes are append-only full-state rows; one open alert per `(event, source, zone)` enforced by a partial unique index; acknowledgement is a row keyed by `(alert, escalation change)` (see DD36) | Current state in one join, complete history, no duplicate alerts, atomic first-click-wins without locks (WEB-23) | [03 §3.9](03-database-schema.md) |
| DD28 | **Compression and retention**: readings compressed after 7 days and kept; forecasts compressed after 2 days and kept 400 days; derived features 180 days; rejected messages 30 days | Under 1 GB per year for five kits; enough history for fine-tuning and a one-year accuracy report | [03 §3.14](03-database-schema.md) |
| DD29 | **One WebSocket per browser**: a leader tab (Web Locks) holds the socket and re-broadcasts events to other tabs over `BroadcastChannel` | One connection and one alert sound per browser; all tabs see the same event stream | [13 §13.3.1](13-frontend-performance.md) |
| DD30 | **Forecasts addressed by run ID and cached as immutable** (`Cache-Control: immutable`, memoized chart options per run) | Runs never change (AL-12); switching or comparing runs costs no request | [13 §13.3.3](13-frontend-performance.md) |
| DD31 | **Columnar time series with an implicit time axis** (`start`, `step_s`, arrays; `null` for gaps) via `format=columnar` | Smaller payloads, no per-point objects, arrays fed directly to charts; gaps shown honestly | [13 §13.3.4](13-frontend-performance.md) |
| DD32 | **Live data in fixed-size typed-array ring buffers; rendering coalesced to one update per animation frame**, urgent (banner, tiles) vs deferred (charts); nothing drawn while the tab is hidden | Handles 60× replay without dropped frames; flat memory over a shift; the alert banner is never delayed | [13 §13.3.5](13-frontend-performance.md) |
| DD33 | **Critical-first loading**: route-level code splitting (admin chunks never downloaded by operators), modular ECharts, lazy Leaflet, banner and tiles before charts | Small login and dashboard bundles; alert state visible first | [13 §13.3.7](13-frontend-performance.md) |
| DD34 | **Freshness on server time and a degraded polling mode** when WebSockets fail but REST works | Stale data never looks fresh; alerts stay visible behind proxies that block WebSockets (NFR-04) | [13 §13.3.8](13-frontend-performance.md) |
| DD35 | **Only immutable data is persisted in the browser** (forecast runs, model reports in IndexedDB, cleared on logout); no service worker or offline mode | An early-warning dashboard must never show outdated alert state as current | [13 §13.3.9](13-frontend-performance.md) |
| DD36 | **Every escalation needs a new acknowledgement**: `created` and `upgraded` (higher level, or watch → warning → live) clear the acknowledged state; downgrades keep it. Earlier acknowledgements remain as history. Firmware stays in a history table (not per reading) and the DD28 retention policy is confirmed by the owner | Operators must confirm they saw the more serious state (owner decision); first-click-wins stays atomic via the `(alert_id, change_id)` key | [03 §3.9.3](03-database-schema.md), [02 §2.6.7](02-api.md) |
| DD37 | **Flat config keys with group prefixes and units in the name** (`wind_orange_kmh`, `alert_warning_on_prob`) | Matches the names already used in the requirements (04 §4.7, CFG-02); easy to read in YAML and errors | [04 §4.1](04-configuration.md) |
| DD38 | **Region defaults and computed defaults** fill the default level: `region_type` selects per-region defaults (heatwave), onboarding supplies computed defaults (rain intensity percentile); site and kit still override the single resolved key | One set of keys, no unused per-region keys; site-specific defaults without manual entry | [04 §4.2](04-configuration.md) |
| DD39 | **Watch/Warning probability cut-offs only at default and site level** | One alerting policy per site; zones differ by thresholds (local risk), keeping site combination (AL-14) explainable | [04 §4.3.7](04-configuration.md) |
| DD40 | **Security, rate-limit and retention settings are default-only** (`defaults.yaml` / local overrides file, restart to apply), not editable in the UI | Operational settings of the installation, not site configuration; reduces risk of locking everyone out from the UI | [04 §4.3.9](04-configuration.md) |
| DD41 | **YAML import and export** of site, kits and recipients, validated exactly like UI saves, atomic, audited; `start.ps1 -Seed` uses it for the demo | Fast, repeatable demo setup and backup; one validation path | [04 §4.6](04-configuration.md) |
| DD42 | **Strict contract validation**: exactly the contract fields, any unknown field rejects the message; timestamps more than 7 days old or 1 day ahead are rejected | DP-12 and the final contract (D25); firmware drift is noticed at once instead of silently tolerated (owner decision) | [05 §5.2](05-data-pipeline.md) |
| DD43 | **Duplicates**: identical resends dropped silently; a differing message with the same `(kit_id, ts)` keeps the first reading and is logged as `conflicting_duplicate` | DP-02 and DP-03 (raw never overwritten); exposes clock or firmware bugs (owner decision) | [05 §5.2.4](05-data-pipeline.md) |
| DD44 | **BME280 → DHT11 fallback**: when BME280 temperature or humidity is faulty, the DHT11 value is used and marked suspicious; pressure has no backup | Heat monitoring continues during a BME280 fault while the lower accuracy stays visible (owner decision) | [05 §5.4.5](05-data-pipeline.md) |
| DD45 | **Late readings up to 3 h** cause recomputation of derived features for all later readings of that kit; older ones are stored (and folded into the aggregates only while inside their refresh windows, 3 h / 26 h; **Revised**, analysis AN-21) but not used for features or live alerts. Clock offset and lateness are derived from `received_at − ts`, not stored | Matches the 3 h aggregate refresh window (DP-08); keeps the schema normalized (owner decision) | [05 §5.5.3](05-data-pipeline.md) |
| DD46 | **Hourly series are end-labelled** (10:00–11:00 is labelled 11:00) and values below 80 % coverage are NULL | Same convention as Open-Meteo/ERA5 training data; gaps are never read as zero rain or calm wind | [05 §5.7](05-data-pipeline.md) |
| DD47 | **QC per measurement with spike re-anchoring**: a jump confirmed by 3 following readings becomes an accepted level change; humidity ≥ 99 % is not stuck-checked; the neighbour check needs ≥ 3 kits | Real sudden changes (squall temperature drops) are not discarded; fewer false faults | [05 §5.4](05-data-pipeline.md) |
| DD48 | **Darts** for the TFT, LightGBM quantile and naive baselines and back-testing; `lightgbm` for event classifiers; `chronos-forecasting` for Chronos-Bolt | One framework with multivariate targets, all covariate types, quantile loss and TFT explainability (owner decision) | [06 §6.1](06-ml-training.md) |
| DD49 | **24 fixed training locations** (8 plains, 8 coastal, 8 hilly), of which **3 are held out** to test the global model at unseen locations | Reproducible training (owner decision, refines D20); direct evidence for ML-05 | [06 §6.2](06-ml-training.md) |
| DD50 | **Hourly model features from one shared module** (`ews.ml.features`) in training and inference; **global** standardisation (no per-location fitting); rain as `log1p` | Identical inputs offline and live; a new site needs no fitting (ML-05) | [06 §6.4–6.5](06-ml-training.md) |
| DD51 | **TFT predicts 9 quantiles** (P02…P98); only P10/P50/P90 are stored; the full set is used to derive probabilities | Alert thresholds lie in the tail beyond P90 (owner decision) | [06 §6.8.2](06-ml-training.md) |
| DD52 | **Probabilities from both TFT quantiles and LightGBM classifiers, isotonic-calibrated, selected per event on validation** (Brier, then PR-AUC), each with a fallback; test only reported | "Final model per hazard from test results" without tuning on the test set (owner decision) | [06 §6.8.5](06-ml-training.md) |
| DD53 | **Model folders + `registry.json`** with semantic versions (major = feature change), SHA-256, pinned library versions, a feature contract checked at load, and active/fallback model per variable and event | ML-09; a wrong or stale model can never be loaded silently | [06 §6.11](06-ml-training.md) |
| DD54 | **Data sources**: ERA5 via the Open-Meteo Archive API (1991–2025); lead-correct archived forecasts (Previous Runs API) for validation and test; stitched Historical Forecast data only for stage-2 training | Consistent history everywhere; honest test scores despite limited forecast archives (D28) | [06 §6.3](06-ml-training.md) |
| DD55 | **Probability windows are part of the model definition**: gust 3 h blocks (0–24 h) and 6 h blocks (24–72 h); rain intensity 3 h blocks (0–6 h); 24 h rain per IMD rain day ending 03:00 UTC; heatwave per local day D1–D3. **Revised (D30, DD99):** heatwave also D0 (rest of today) at run time | Classifiers are trained for fixed windows; worker and alert engine use the same ones | [06 §6.6](06-ml-training.md) |
| DD56 | **Rolling hours**: each 15-minute run feeds the hourly TFT with hours ending at its issue time (built from four 15-minute buckets); Open-Meteo inputs are interpolated to those offsets | Every run sees new data, so run-counting rules (AL-09, AL-11) are meaningful; no retraining needed (owner decision) | [07 §7.3](07-forecast-worker.md) |
| DD57 | **Gaps**: ≤ 3 h interpolated; longer gaps and new kits filled with bias-corrected Open-Meteo pseudo-observations and marked `degraded`; no data for 24 h → kit skipped | New kits get forecasts from day one; outages do not stop forecasts for a week; the UI stays honest (owner decision) | [07 §7.4](07-forecast-worker.md) |
| DD58 | **Missed runs are not back-filled**; a run that cannot start within 5 min of its slot is skipped | The current forecast is never delayed by catching up (owner decision) | [07 §7.1](07-forecast-worker.md) |
| DD59 | **A classifier is used only at the threshold it was trained for**; overridden (local-risk) thresholds use TFT-derived probabilities. **Revised (DD121):** a non-zero heatwave normal offset counts as a changed threshold | Classifier outputs answer a fixed question; quantiles work for any threshold | [07 §7.5](07-forecast-worker.md) |
| DD60 | **Persistent inference child process** with models loaded once, hard timeout and automatic restart | Fast runs without reloading models; model crashes never stop the scheduler | [07 §7.2](07-forecast-worker.md) |
| DD61 | **Chronos-Bolt shadow runs hourly**, stored as separate `is_shadow` runs, never used for alerts | Phase-2 comparison (requirements 05 §5.6) at a quarter of the CPU cost | [07 §7.6](07-forecast-worker.md) |
| DD62 | **Four alert events** (`gust`, `rain_intensity`, `rain_24h`, `heatwave` with orange = heatwave, red = severe); a **squall is a trigger** of the live gust alert, not an event; one severity order (colour first, then watch < warning < live) | One alert per zone shows the most severe colour (owner decision); heatwave → severe heatwave is an upgrade of the same alert | [08 §8.2](08-alert-engine.md) |
| DD63 | **Forecast state per run**: the most severe qualifying colour with hysteresis (`watch_off` keeps current and lower colours), Warning by `warning_on`/`warning_off`; upgrade on one run, downgrade/cancel after 3 lower runs, far episodes need 2 agreeing runs, clear when the window has passed | AL-08 – AL-11 with one explicit rule set | [08 §8.5](08-alert-engine.md) |
| DD64 | **Live minimum duration = rolling median** over the duration window (≥ 80 % coverage); clear-down when the current colour stops holding for the clear-down time; offline kits are "unknown", cleared after 60 min without data | Single gusts ignored, one lull does not reset the timer (owner decision); no false clears during outages | [08 §8.6](08-alert-engine.md) |
| DD65 | **Live takes over forecast** at the same or higher colour (requirements D29). **Revised (DD103):** only a forecast alert whose window includes now | One alert thread per event (owner decision) | [08 §8.7](08-alert-engine.md) |
| DD66 | **Combination as AL-14**: heatwave and heavy rain as site alerts (median = lower middle for even counts / worst kit), wind per zone with site status = worst zone; every kit first evaluated with its own thresholds | Owner decision; local risk respected; one hot rooftop cannot raise a site heatwave alone | [08 §8.8](08-alert-engine.md) |
| DD67 | **Suppression silences emails only**; colour rise overrides it; certainty rise at the same colour does not. **Revised (D36, DD102):** the alert's end (cancel/clear) is always emailed | AL-15; the alert stays visible and evaluated | [08 §8.9](08-alert-engine.md) |
| DD68 | **Escalations bypass cooldown**; downgrades, cancels and clears within the cooldown are queued and superseded by newer changes | AL-06 without ever delaying a more serious message | [08 §8.11](08-alert-engine.md) |
| DD69 | **Two email audiences rendered at send time**: recipient lists get level, type, hazard, zone, window and advice only; operators/admins add probabilities, trend, source and an acknowledge link; state comes from the change, advice is the latest | WEB-42, WEB-43; advice edits reach delayed emails | [09 §9.4](09-notifications.md) |
| DD70 | **Subject format** `[LEVEL TYPE] Change: Hazard – Zone – Window` with fixed window formats; `[CANCELLED]`, `[CLEARED]`, `[MAINTENANCE]` prefixes | WEB-40; readable in any inbox | [09 §9.3](09-notifications.md) |
| DD71 | **Retries**: exponential backoff from 30 s (cap 15 min, 6 attempts) for temporary errors; 5xx fails at once; failed account emails print their link to the console | WEB-44, WEB-03 | [09 §9.7](09-notifications.md) |
| DD72 | **One email thread per alert** via `Message-ID` / `References`; `Auto-Submitted: auto-generated` | Created → upgraded → cleared read as one conversation; no auto-reply loops | [09 §9.8](09-notifications.md) |
| DD73 | **Only the newest unsent change per alert and address is sent**; older queued ones are skipped as superseded | Cooldown and mailer outages never produce bursts of outdated alerts | [09 §9.6](09-notifications.md) |
| DD74 | **Acknowledge links never change state on GET**: they open the alert page, which asks for confirmation after login | Safe against link scanners and CSRF | [09 §9.4.2](09-notifications.md) |
| DD75 | **Maintenance notices are emailed once, when they open**; closing is shown in the UI only | Less noise for operators | [09 §9.9](09-notifications.md) |
| DD76 | **Persistent alert banner** on every page with the most severe active alert, counts, needs-acknowledgement and inline Acknowledge | Alert state first, on every screen | [10 §10.3](10-ui.md) |
| DD77 | **Levels always as colour + icon + text** with WCAG AA contrast | Colour-blind users and grey-scale printouts | [10 §10.1](10-ui.md) |
| DD78 | **Operator panel = alert detail side panel + "Raise alert" dialog**, not a separate page | Actions where the operator is already looking (07 §7.2 operator panel) | [10 §10.2](10-ui.md) |
| DD79 | **First-run wizard**: admin → site (form or YAML) → kits → recipients → onboarding progress, dashboard usable during onboarding | WEB-01, CFG-07 in one guided flow | [10 §10.6](10-ui.md) |
| DD80 | ~~Desktop first, phone-ready alerts pages~~ **Revised (D34):** **desktop only**, used on the server machine; no phone layout is required | The dashboard is not reachable from phones or other computers (owner decision, analysis AN-27) | [10 §10.1](10-ui.md) |
| DD81 | **Forecast chart**: P10–P90 band, P50, observed overlay, Open-Meteo line, threshold lines, shaded alert windows; probability table per level and window outlined at the cut-offs | Shows uncertainty, thresholds and alerts together | [10 §10.4.2](10-ui.md) |
| DD82 | **One clock abstraction** (`ews.common.clock`: real, demo, fake); in demo mode the simulator's `sim/clock` drives all backend time except security | Accelerated replay (TST-01, Scenario 9) works end to end; deterministic tests | [11 §11.3](11-simulator.md) |
| DD83 | **Scenario files in YAML** (baseline + set/ramp/step/hold/noise segments); built-ins mirror the real-time scenarios | Demo scripts and test cases from the same files | [11 §11.4.2](11-simulator.md) |
| DD84 | **Replay generator**: hourly ERA5 or kit CSV → 1-minute data with turbulence, stochastic gust factor and Poisson rain tips; sensor model with BME/DHT noise and resolution | Realistic minute data from hourly history | [11 §11.4.1](11-simulator.md) |
| DD85 | **Multi-kit spatial model**: shared weather + elevation lapse, exposure factors, AR(1) local noise, moving fronts and rain cells | Exercises neighbour QC and combination rules realistically (TST-04) | [11 §11.6](11-simulator.md) |
| DD86 | **Faults as overlays** on any mode, incl. disconnect without DISCONNECT (last will), silent kit, late delivery, conflicting duplicates | Every QC and status path testable on demand (TST-03) | [11 §11.5](11-simulator.md) |
| DD87 | **Simulator keeps its own copy of the contract schema**, checked against the backend validator in tests | DD7 independence without contract drift | [11 §11.2](11-simulator.md) |

| DD96 | **Structured JSON-line logs** per process with stable `event` codes and IDs linking to database rows; rotation 10 MB × 10; secrets never logged | Easy to search and to use in tests; no secret leaks (NFR-08) | [14 §14.2](14-operations.md) |
| DD97 | **Daily `pg_dump` backups** (custom format, 7 daily + 4 weekly) plus private copies of `.env` and the Mosquitto password file; demo and test databases not backed up | Simple, works while running, small | [14 §14.3](14-operations.md) |
